# CLAUDE.md

Notes for AI assistants (Claude Code in particular) working in this repo.
For humans: see `README.md`, `development.md`, `deployment.md`, and
`CONTRIBUTING.md` instead.

## Repository layout

This is a Bun-workspace monorepo with a separate Python backend.

```
backend/    FastAPI + SQLModel + Alembic (Python 3.10+, uv)
frontend/   React 19 + Vite + TanStack Router/Query + Biome (Bun)
extension/  Browser extension (Chrome/Firefox/Edge/Opera/Safari) — Vite + Vitest
mobile/android/  Android Trusted Web Activity wrapper (bubblewrap-generated)
mobile/ios/      iOS app configuration (PWABuilder-generated)
landing/    Static landing page (Cloudflare Workers; Nginx container locally)
scripts/    Build/generation helpers
```

The frontend and extension both consume an OpenAPI client auto-generated
from the backend's `/api/v1/openapi.json`. **Never hand-edit
`frontend/src/client/` or `extension/src/client/`** — they are
regenerated by `bun run generate-client`.

## Running locally

```bash
docker compose up -d   # Postgres + Mailcatcher + backend + frontend
```

Once up:
- Frontend: http://localhost:5173
- Backend OpenAPI docs: http://localhost:8000/docs
- Mailcatcher UI: http://localhost:1080

`compose.override.yml` adds dev-only volumes and reload-on-change for both
servers.

## Day-to-day commands

```bash
# Backend
cd backend && uv run pytest --cov=app --cov-report=term-missing
cd backend && uv run mypy app
cd backend && uv run ruff check app tests && uv run ruff format --check app tests
cd backend && uv run alembic revision --autogenerate -m "<message>"
cd backend && uv run alembic upgrade head

# Frontend
cd frontend && bun run dev               # vite
cd frontend && bun run build             # tsc + vite build
cd frontend && bun run lint              # biome (with --write --unsafe)
cd frontend && bun run generate-client   # regenerate src/client/ from backend OpenAPI
cd frontend && bun run test              # playwright E2E

# Extension
cd extension && bun test                 # vitest unit tests
cd extension && bun run build

# Everything
prek run --all-files                     # ruff + mypy + biome + client regen
```

`prek` is the project's pre-commit runner (faster reimplementation).
Never use `--no-verify` — fix the underlying issue.

## Conventions to follow

**Units**
- Always read unit choices from `UnitSchema.enum` (`frontend/src/client/schemas.gen.ts`).
  Never hardcode arrays of units — the backend `Unit` enum is the source of truth.
- Display unit labels via the `common` namespace:
  `tCommon(\`unit_labels.${u}\`, { defaultValue: u })`.
- The shared `<UnitSelect>` (`frontend/src/components/Common/UnitSelect.tsx`)
  wraps this pattern. Prefer it over building a Select from scratch.

**Mutations**
- Use the `useCrudMutation` hook (`frontend/src/hooks/useCrudMutation.ts`)
  for any CRUD action that follows the standard
  `success-toast / error-toast / invalidate-key` pattern. It bakes in
  `handleError.bind(showErrorToast)` and supports multi-key invalidation.
- Use raw `useMutation` only when you need richer lifecycle hooks
  (optimistic updates, custom `onMutate`, etc.).

**Confirmation dialogs**
- Destructive flows use `<ConfirmDialog variant="destructive">`
  (`frontend/src/components/Common/ConfirmDialog.tsx`). Supports both
  controlled mode (caller holds `open`) and trigger mode (caller renders
  the trigger child — e.g. a `DropdownMenuItem`).

**Forms**
- The recipe Add/Edit flow shares one `<RecipeForm>`
  (`frontend/src/components/Recipes/RecipeForm.tsx`) with a `mode` prop
  and an optional `importPanel` slot. Schema lives in
  `recipeFormSchema.ts` (factory + `buildEditDefaults` + create/update
  payload mappers). When adding a new recipe field, add it to
  `RecipeFormValues`, `createRecipeFormSchema`, `defaultCreateValues`,
  `buildEditDefaults`, and both payload mappers.
- React Hook Form + Zod (`@hookform/resolvers/zod`) is the standard
  combination. Cast to `Resolver<MyValues>` only when the schema includes
  `z.coerce` for inputs.

**i18n**
- Strings live in `frontend/src/i18n/locales/{en,fr}/<namespace>.json`.
- Every new key must land in both `en` and `fr` simultaneously.
- Use the shared `common` namespace for verbs (`cancel`, `save`,
  `delete`), unit labels, and other cross-feature strings.
- Browser language detection is automatic — never read `navigator.language`
  directly.

**Backend public schemas**
- Models live in `backend/app/models/`; CRUD lives in `backend/app/crud/`.
- Public-facing shapes are derived through helper functions:
  - `recipe_to_public(recipe, owner?)` and
    `recipe_ingredient_to_public(ri)` in `crud/recipe.py`
  - `shopping_list_to_public(list)` in `crud/shopping_list.py`
- Reuse those helpers instead of building `RecipePublic` / `ShoppingListPublic`
  inline.
- Always supply keyword-only arguments (`session=session`, `owner_id=…`)
  — the CRUD layer enforces this with `*`.

**Recipe import package**
- `backend/app/services/recipe_import/` is split by concern:
  `models.py`, `prompt.py`, `scraper.py`, `llm.py`, `orchestrator.py`.
- The orchestrator imports its dependencies via `llm as llm_module` and
  `scraper as scraper_module`. Tests mock at the submodule paths
  (`app.services.recipe_import.scraper.fetch_page`,
   `app.services.recipe_import.llm.get_llm`).
- LangSmith tracing is opt-in via `LANGCHAIN_TRACING_V2` +
  `LANGCHAIN_API_KEY` env vars.

**Visual identity**
- See `VISUAL_IDENTITY.md`. Colors are OKLCH semantic tokens — never
  hardcode hex. Use Tailwind utility classes that map to the design
  tokens (`bg-primary`, `text-destructive`, etc.). Light/dark mode is
  driven by `ThemeProvider` (`frontend/src/components/theme-provider.tsx`).

## CI pipelines (`.github/workflows/`)

Each push runs:
- `pre-commit.yml` — ruff, mypy strict, biome, OpenAPI client regen check
- `test-backend.yml` — pytest with 90% coverage gate
- `playwright.yml` — frontend E2E (4-shard parallel, retries on CI)
- `test-extension.yml` — vitest + type-check + build
- `test-docker-compose.yml` — bring up the full stack as a smoke test
- `deploy-cloudflare.yml` — on `master`, deploy `frontend/` + `landing/` to staging

On release tags:
- `publish-extension.yml` — publish to Chrome, Firefox, Edge, Opera, Safari
- `publish-stores.yml` — Play Store, F-Droid, App Store
- `deploy-cloudflare.yml` — deploy `frontend/` + `landing/` to production

`bump-version.yml` is manually dispatched and bumps the root
`package.json`, `frontend/package.json`, `extension/package.json`,
`backend/pyproject.toml`, and the extension manifest in lockstep.

Deployment is split in two (see `deployment.md`):

- `frontend/` and `landing/` are static sites on Cloudflare Workers, deployed
  by `deploy-cloudflare.yml` — `master` → staging, `v*` tag → production.
  Config lives in `frontend/wrangler.jsonc` / `landing/wrangler.jsonc`, and
  build-time settings in the committed `.env.staging` / `.env.production`
  files of each project. `compose.yml` no longer builds them; their Docker
  services live in `compose.override.yml` for local development only.
- `backend/` and the database are deployed by Coolify from `compose.yml` on
  every push to `master` via the Coolify GitHub App.

Domains: `shop-n-cook.com` (landing), `app.shop-n-cook.com` (frontend),
`api.shop-n-cook.com` (backend); staging mirrors this under
`staging.shop-n-cook.com`.

## Things not to touch

- `frontend/src/client/` and `extension/src/client/` — generated.
- `frontend/src/components/ui/` — shadcn-generated primitives. Edit the
  caller, not the primitive.
- `backend/app/alembic/versions/*.py` — generated by Alembic.
- Anything under `node_modules/`, `.venv/`, `bun.lock`, `uv.lock`.
